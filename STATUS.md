## Что реализовано на H0

```text
backend/
  config.py            настройки из окружения, БД и порт по умолчанию
  db.py                подключение к SQLite, явные миграции, версия схемы
  main.py              создание приложения, статика, безопасный ответ 500
  migrations/          правила миграций; доменных миграций пока нет
  routes/health.py     GET /api/health
  routes/pages.py      GET / (корневая HTML-страница)
frontend/
  index.html           корневая страница: назначение проекта, статус API, разделы
  css/styles.css       светлая и тёмная схемы, адаптивность, focus, reduced motion
  js/app.js            запрос /api/health с состояниями loading/ok/empty/error
tests/                 conftest, health, pages, migrations (временная БД)
scripts/migrate.py     CLI явного применения миграций
requirements.txt       fastapi, uvicorn
requirements-dev.txt   pytest, httpx
Dockerfile, docker-compose.yml, .env.example, pytest.ini, .dockerignore
```

Контракт совместимости сохранён: `GET /api/health` возвращает `{"status":"ok"}`.
Добавлены совместимые поля `database` и `schema_version`; при недоступной БД
возвращается 503, а не успешный ответ. `content/verified_content.json` не
импортируется: явный импорт появится отдельной командой на H2.

## Решения

- Тема на H0 следует системной настройке `prefers-color-scheme`. Явный переключатель
  с сохранением выбора и меню — задача H1, в H0 не дублируется.
- Разделы показаны как «материалы готовятся» без ссылок: мёртвых ссылок и заглушек
  в публичном пути нет.
- Служебная таблица `schema_migrations` создаётся всегда, это учёт миграций, а не
  данные. Первая доменная миграция (пользователи, сессии) появится на H3.
- Только подтверждённые факты: название, назначение, университет, направление,
  куратор практики. Выдуманных контактов, дат и ролей нет.

## Блокеры

Для H0 нет. Для H1 нужны только код и вёрстка. Для H2 требуются материалы из
`CONTENT.md`: минимум ещё две новости, текущий состав команды и подтверждённые
контакты.

- Пересборка живёт только в `feature/hermes-rebuild`. Ветка запушена на GitHub
  (commit `8cc1529`), работа продолжается в ней.
- `feature/hermes-rebuild` создана как orphan-ветка: общей истории с `main` нет,
  поэтому push в `main` возможен только через force push и уничтожил бы историю
  продакшна.
- В репозитории есть workflow `test-and-deploy.yml`, срабатывающий на push в `main`
  и умеющий запускать деплой на VPS: ещё одна причина не пушить в `main`.
