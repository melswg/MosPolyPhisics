# Безопасный перенос данных

## Принцип

Новая версия не подключается к production SQLite напрямую и не получает копию
пользователей, password hashes, сессий или reset-токенов. Сначала строится новая
схема на локальной БД, затем публичный контент импортируется явной проверяемой
командой. Обычный startup ничего не подмешивает.

## Источники

1. `content/verified_content.json` — разрешённый стартовый пакет.
2. Материалы, которые пользователь позже передаст и подтвердит.
3. Отдельный JSON/CSV export только публичных таблиц старой версии после аудита.

Live API и старая БД не являются автоматически доверенным источником: в них есть
demo-seed и неподтверждённые записи.

## Что переносить

- подтверждённые новости;
- подтверждённые цитаты с источником;
- опубликованные видео с разрешённым URL и описанием;
- реальные события;
- материалы новеллы и ссылка на существующую сборку;
- проверенные вопросы, варианты, ответы и объяснения.

## Что не переносить без отдельного решения

- пользователей и их hashes;
- session/reset tokens;
- роли и административные права;
- логи, backups, `.env`, SMTP и deploy secrets;
- любые строки, классифицированные как demo/unverified;
- абсолютные локальные пути и URL preview-сервера.

## Требование к будущему importer

- отдельная CLI-команда с явным путём к целевой БД;
- dry-run с количеством create/skip/reject;
- валидация структуры и обязательного provenance;
- идемпотентность по стабильному `source_id` либо естественному ключу;
- только добавление/обновление выбранных публичных сущностей;
- транзакция и rollback при ошибке;
- не удалять строки, которых нет в файле;
- тестировать только на временной БД;
- вывести итог без содержимого секретных полей.

## Переключение новой версии

1. Создать backup текущей production БД и проверить восстановление отдельно.
2. Поднять preview на другой БД/порту.
3. Импортировать подтверждённый публичный export в preview.
4. Сравнить количество и выборку материалов, пройти browser smoke test.
5. Отдельно решить судьбу аккаунтов; по умолчанию пользователи регистрируются заново.
6. Только после разрешения выполнить production cutover с documented rollback.

Ни один из этих шагов не выполняется Hermes автоматически.
